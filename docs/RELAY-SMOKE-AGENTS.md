# Relay smoke: AI agents chatting (Hermes-driven)

Option B of the relay smoke suite. Unlike the deterministic delivery gate
(scripts/smoke/relay-smoke.sh), this spins up N Sonar identities that hold real
conversations: each reply is generated by an LLM via a configurable command
(Hermes by default) and sent back over sonar-cli.

## How it works

A single orchestrator (scripts/smoke/relay-smoke-agents.sh) owns the loop:

1. Provisions N ephemeral Sonar identities + a seeded random graph of partners.
   With `WITH_WHITENOISE=1`, it also provisions one isolated upstream White
   Noise CLI identity and adds it to the graph.
2. In White Noise mode, runs a deterministic preflight with two fresh Sonar
   identities so Sonar→White Noise and White Noise→Sonar each exercise new
   KeyPackage/group/welcome creation independently.
3. Seeds a static opening line on each edge (no LLM cost for openers).
4. For ROUNDS rounds: each identity drains new inbound; for each message the
   orchestrator builds a persona-driven prompt, calls the reply command, and
   sends the reply back.
5. Reports message flow, reply latency, errors, and the classified White Noise
   preflight result, and writes a conversation log.

The reply command receives the prompt in $AGENT_PROMPT and prints the reply on
stdout. Default uses Hermes:

    AGENT_REPLY_CMD='hermes chat -q "$AGENT_PROMPT" --yolo'

One hermes chat call per reply uses the Hermes model provider; no N gateways are
needed. Override for any backend (OpenAI, Ollama, ...) or a dummy.

## Run on a Hermes host

    ( cd core && cargo build -p sonar-cli --release )
    scripts/smoke/relay-smoke-agents.sh
    IDENTITIES=3 FANOUT=1 ROUNDS=3 scripts/smoke/relay-smoke-agents.sh

## Run with a real White Noise peer

Build/install the upstream `wn` and `wnd` binaries first. They remain external
AGPL processes; Sonar does not link or vendor `whitenoise-rs`.

    # from a whitenoise-rs checkout
    cargo build --release -p whitenoise-cli --bin wn --bin wnd

    # run the real interop preflight and then include White Noise in the graph
    WITH_WHITENOISE=1 \
      WN_BIN="$HOME/.local/bin/wn" WND_BIN="$HOME/.local/bin/wnd" \
      IDENTITIES=3 FANOUT=1 ROUNDS=2 \
      scripts/smoke/relay-smoke-agents.sh

The default target is `wss://nostr.relay.hedwig.sh`. White Noise gets its own
temporary data directory, logs, Unix socket, and daemon PID under the run work
directory; the harness never touches a user's normal White Noise daemon or
exports an nsec. On failure, the work directory is retained automatically and
the final stderr line names it. Use `KEEP_WORK=1` to retain a successful run.
`WN_RELAYS` defaults to Hedwig plus `relay.damus.io` and `nos.lol`: upstream
White Noise expects a relay quorum for live subscriptions. The CLI's relay
status can be stale, so the preflight treats it as diagnostic and instead arms
and verifies a long-lived account notification subscription before Sonar sends.
Sonar itself continues to use Hedwig only.

Each direction reports independently and the second direction still runs if the
first fails. The graph also always contains at least one Sonar→White Noise and
one White Noise→Sonar edge, even when the preflight is disabled.

The preflight classifies failures at the boundary where they occur:

- `sonar_key_package_fetch`
- `sonar_group_or_send`
- `whitenoise_key_package_fetch`
- `whitenoise_welcome_or_message_not_seen`
- `whitenoise_adapter_or_daemon`
- `whitenoise_relay_or_subscription`
- `whitenoise_group_or_send`
- `sonar_welcome_or_message_not_seen`
- `sonar_listener_not_ready`

`KEYPACKAGE_SEND_ATTEMPTS` (default 6), `WN_KEYPACKAGE_TIMEOUT_SECS` (45),
`WN_MESSAGE_TIMEOUT_SECS` (30), and `INTEROP_CONNECT_DELAY_SECS` (3) are
bounded diagnostics tunables. A first Sonar send failure followed by success is
recorded in `whitenoise_preflight.sonar_to_whitenoise.error` instead of being
hidden. The script always emits final metrics, then exits non-zero if either
deterministic direction failed.

## Test the plumbing without Hermes

Point AGENT_REPLY_CMD at a dummy so every part except the model runs against the
live relay (use a relay that delivers, e.g. damus):

    TARGET_RELAY=wss://relay.damus.io AGENT_REPLY_CMD='printf ack' \
      IDENTITIES=2 FANOUT=1 ROUNDS=1 scripts/smoke/relay-smoke-agents.sh

Expect messages_sent=2, messages_received=1, replies_generated=1 and a non-empty
conversation log.

RECEIVE_TIMEOUT_SECS (15), MAX_REPLY_CHARS (300), AGENT_REPLY_CMD, SEED,
WITH_WHITENOISE (0), WHITENOISE_PREFLIGHT (1), WN_BIN, WND_BIN,
WN_RELAYS (Hedwig plus two bootstrap relays),
KEYPACKAGE_SEND_ATTEMPTS (6), WN_KEYPACKAGE_TIMEOUT_SECS (45),
WN_MESSAGE_TIMEOUT_SECS (30), INTEROP_CONNECT_DELAY_SECS (3), KEEP_WORK (0).

## Relationship to the gate

scripts/smoke/relay-smoke.sh is the assertable daily delivery gate
(deterministic payloads). This script is the realism layer: it exercises real
conversation content and load. Run both; the gate stays the pass/fail signal and
this one is qualitative.
